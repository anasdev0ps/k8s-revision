1 Analogy (Samajhne ke liye)

GatewayClass: "The type of gate" (kya yeh lakri ka darwaza hai ya lohe ka? e.g. Traefik ya Envoy).

Gateway: "The actual gate/door" (kahan laga hua hai aur kounsa tala (port/TLS) hai).

HTTPRoute: "The sign board" jo visitor ko batata hai ke "Agar /app1 jana hai toh is raste par jao".

2 Core Concepts

  • Ingress-nginx is retiring: Purana Ingress object out-date ho raha hai, ab modern tareeqa **Gateway API** hai.
  • Gateway API Implementations: Traefik, Envoy Gateway, ya NGINX Gateway Fabric me se koi ek install karna parta hai.
  • Separation of Duties: Platform team sirf Gateway (door) banati hai, aur App developers apne apne HTTPRoute (signs) banatay hain. Yeh purane Ingress se boht secure aur clean tareeqa hai.

3 Hands-on Steps (Every Routing Type)

  1. Path-based: Request agar /app1 aaye toh Service A ko bhejo, /app2 aaye toh Service B.
  2. Host-based: Agar traffic blue.duckdns.org se aaye toh Blue app, agar green.duckdns.org aaye toh Green app. (Ye Blue-Green deployments ke liye prep hai).
  3. Weighted / Traffic Split: 90% traffic v1 par bhejo, aur 10% naye v2 (Canary) par.
  4. TLS termination: cert-manager aur Let's Encrypt ke zariye real domain par HTTPS enabled karein.

4 Errors to Break + Fix

  • 502/503 (Bad Gateway): Agar backend (Service ya Pod) down ho, ya HTTPRoute mein ghalat port likha ho.
  • Wrong `parentRef`: Agar HTTPRoute ne Gateway ka naam ghalat likha ho toh traffic attach nahi hoga.
  • Cert not ready: Agar Let's Encrypt TLS certificate issue hone mein time lagaye toh HTTPS error aayega.

5 Best Practices (Pro Tips)

  • Naye Kubernetes projects mein hamesha Gateway API use karein bajaye Ingress ke.
  • RBAC (Role-Based Access Control) use kar ke developers ko sirf HTTPRoute create karne ki permission dein, Gateway create karne ki nahi.
  • Certs ko hamesha cert-manager ke zariye automate karein.

Done-Check

  • Tamam routing types (Path, Host, Split) test ho chuki hain, aur HTTPS real domain par successfully kaam kar raha hai!
