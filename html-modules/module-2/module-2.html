Module 2

Services & Basic Networking

Pods ephemeral hote hain (unke IP addresses badalte rehte hain). Is module mein hum seekhenge ke in badalte hue Pods tak traffic ko reliably kaise pohnchaya jaye, jo ke Kubernetes Services ka kaam hai.

Receptionist
(Kubernetes Service)
Waiter 1
(Pod A - 10.1.1.1)
Waiter 2
(Pod B - 10.1.1.2)
Analogy: Service = Restaurant ki Receptionist. Pod = Waiter. Agar koi waiter kaam chor de aur naya waiter aaye (Pod delete ho kar naya ban jaye), toh customer ko farq nahi parta kyunke wo order Receptionist (Service) ko deta hai, aur wo khud dekhti hai ke konsa waiter free hai.

Hum Kya Seekhenge (Concepts)

  • ClusterIP: Default service. Sirf cluster ke andar ke pods isay access kar sakte hain.
  • NodePort: Cluster ke bahar se access karne ke liye (host VM ki IP aur ek specific port ke zariye).
  • LoadBalancer: Cloud provider ka external load balancer attach karne ke liye (jaise Azure load balancer).
  • CoreDNS: Kubernetes ka apna DNS system jo Service ke naam (jaise `my-app-service`) ko uski IP mein translate karta hai.

Hands-on Steps

  1. Ek ClusterIP service banayein aur doosre pod se usay access karke check karein.
  2. Us service ko modify karke NodePort banayein, aur apni host VM ki IP se browser mein access karein.
  3. Nodes ke andar ja kar iptables aur IPVS rules check karein jo Kubernetes ne automatically banaye hain.

Errors (Jo hum break karke fix karenge)

Hum jaan boojh kar in issues ko create aur fix karenge:

  • TargetPort Mismatch: Jab Service ghalat port par traffic bheje (connection refused error).
  • Selector Mismatch: Jab Service ko Pods na milein, aur uske `Endpoints` empty show hon.

Best Practices

  • Hamesha named ports use karein (jaise port ka naam http rakhein, bajaye sirf `80` likhne ke). Is se configuration aasaan rehti hai.
  • Troubleshooting ke liye hamesha kubectl get endpoints command chalayen taake pata chale ke Service pods se connect hui hai ya nahi.
